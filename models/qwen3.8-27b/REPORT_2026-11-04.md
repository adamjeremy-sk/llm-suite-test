# Qwen3.8-27B on an RX 7900 XTX: speculative-decoding speed tuning (2026-11-04)

**Result:** MTP drafting with `--spec-draft-n-max 5 --spec-draft-sampling probabilistic`.
Generation went from **39 t/s with no drafting** to **~90 t/s on short prompts** (99–110 t/s on code),
**87 t/s at 22k tokens of context** and **71 t/s at 50k**. The final step, probabilistic drafting, added
+6.8% (short) and +5.8% (long context) over greedy drafting at no extra cost per step and no extra VRAM.

The bigger cost in agent use is reading the prompt, not generating: a fresh 22k-token prompt takes ~30 s
and a 50k-token prompt ~82 s, and no drafting setting changes that.

Raw reports for every pass are in [`results/`](results/). Server script before/after: [`server/`](server/).

## 2. Method

All passes used the same requests against a running server, one change at a time, with your normal
server script copied and edited per config (never the original).

| Prompt | Kind | Size | Notes |
|---|---|---|---|
| refactor | short | 135 tokens | rewrite a Kotlin function (output copies input: drafts land easily) |
| codegen | short | 82 tokens | write a Kotlin function + 3 JUnit tests |
| prose | short | 36 tokens | ~300-word explanation (hardest to draft) |
| longctx | long | 22,235 tokens | one 112 KB Kotlin file + an edit task |
| xlctx | long | 50,639 tokens | five Kotlin files + the same task (round 2 only) |

- `max_tokens` 1024; seeds 1001, 1002, … so every config sees identical requests. Reasoning is on, so
  generated tokens include thinking.
- Reported speed = llama.cpp's own `predicted_per_second`; medians across runs.
- "Core geo-mean" = geometric mean of refactor, codegen and prose; "long geo-mean" = of longctx and xlctx.
- Each sweep repeats its reference config at the end; the two always agreed within 1.5%.
- Between-session variance of the same config was about 4% (core geo-mean 87.5 in round 1 vs 84.3 in
  round 2), so single differences under ~5% are not meaningful.

These used the suite's v1 prompts (math and logic were added afterwards as v2); the prompt texts and
corpus files are byte-identical to what's in this repo.

## 3. Passes

### Pass 0: false start (draft settings ignored)

The first runs labelled N=0…5 all came out the same (~100 t/s code). The server log showed why:
`mean len` = 1 + 5 × acceptance on every request (e.g. 0.75 → 4.75), i.e. every run drafted 5 tokens.
The server script hard-coded `--spec-draft-n-max 5` and the edits weren't reaching it.
**Lesson:** always confirm the effective draft length, = (mean len − 1) / acceptance, from the log.
The suite's reports now print "avg drafted per check" for every config.

### Pass 1: draft length N = 0…8 (greedy drafting)

5 runs per short prompt. [`results/20261104_101700_draft-length-v1.md`](results/20261104_101700_draft-length-v1.md)

| N | refactor | codegen | prose | core geo | vs N=0 | acceptance | VRAM MiB |
|---|---|---|---|---|---|---|---|
| 0 | 39.3 | 39.0 | 38.8 | 39.0 | — | — | 20,579 |
| 1 | 62.1 | 62.0 | 56.1 | 60.0 | +54% | 0.85 | 21,685 |
| 2 | 78.3 | 82.3 | 64.9 | 74.8 | +92% | 0.75 | 21,824 |
| 3 | 89.1 | 92.4 | **68.2** | 82.5 | +112% | 0.67 | 21,992 |
| 4 | 94.1 | 104.2 | 64.7 | 86.0 | +120% | 0.58 | 22,135 |
| **5** | **99.4** | **104.8** | 62.1 | **86.5** | **+122%** | 0.52 | 22,291 |
| 6 | 97.9 | 102.5 | 58.1 | 83.5 | +114% | 0.46 | 22,423 |
| 7 | 93.1 | 97.6 | 54.7 | 79.2 | +103% | 0.42 | 22,578 |
| 8 | 42.7 | 48.3 | 23.2 | 36.3 | **−7%** | 0.39 | 22,754 |

**Cost model.** Time per verify step ("check") was the same for every prompt type:
**≈ 25.6 ms + 3.8 ms per drafted token** for N ≤ 7. Speed = tokens per check ÷ ms per check, so a drafted
token pays off only if it lands often enough to cover its 3.8 ms (at ~100 t/s, roughly a 40% chance of
being reached and accepted). Code clears that up to N = 5; prose stops clearing it after N = 3.

**N = 8 is a cliff, not a trend:** a check jumps from 54 ms (N = 7) to ~128 ms (N = 8) while acceptance
barely moves (0.42 → 0.39). A 9-token verify batch most likely crosses a Vulkan kernel threshold on this
build. Early stopping (pass 2) didn't avoid it. **N = 7 is the ceiling on this backend.**

- `--spec-draft-p-min` ("early stop when the draft is unsure") hurts prose: at 0.7 prose drafts shrink to
  ~2 tokens but get *slower*, because the draft head's confidence is a poor predictor of acceptance.
- At long context each check costs ~11 ms more regardless of draft length, which makes longer drafts
  worth more — hence p-min 0.7's long-context win.
- **Each 22k-token run took ~42 s: ~30 s reading the prompt (736 t/s) and ~12 s generating.**

**Why probabilistic drafting wins.** The server samples at temperature 0.7. Greedy drafting always
proposes the draft head's top token; probabilistic drafting samples it the way the main model samples,
so its proposals match more often. Measured:

| | refactor | codegen | prose | longctx | xlctx |
|---|---|---|---|---|---|
| acceptance, greedy | 0.64 | 0.73 | 0.36 | 0.74 | 0.74 |
| acceptance, probabilistic | 0.71 | 0.79 | 0.39 | 0.78 | 0.81 |
| ms per check, greedy | 44.7 | 44.7 | 44.3 | 56.3 | 70.5 |
| ms per check, probabilistic | 47.2 | 45.2 | 44.2 | 56.3 | 70.7 |

Same cost per step, more tokens per step. The main model still verifies every token, so the output
distribution is unchanged by design (output quality was not separately measured). It also makes early
stopping unnecessary: it matches p-min 0.7's long-context gain without p-min's short-prompt loss.

**Context depth:** cost per check grows 44.7 → 56.3 → 70.5 ms from short → 22k → 50k tokens, so
generation falls ~100 → 83 → 67 t/s (greedy). **Cold prompt processing:** 734 t/s at 22k (~30 s),
621 t/s at 50k (~82 s), identical across all drafting configs.

**MTP + n-gram copying** (`--spec-type draft-mtp,ngram-mod`) drafted 7–8 tokens at ~0.55 acceptance:
slower everywhere, including the long-context edit task it was meant to help.

## 4. Incident: leftover server spilled the next config into system RAM

During round 2, `n5_prob` loaded in 27 s instead of 6 and ran at ~4 t/s. Two `llama` processes were
running: the previous config's server had closed its port (so the harness thought it had stopped) but
was still exiting and holding ~22 GB of VRAM; it ignored SIGTERM and needed `kill -9`. The new server
spilled into shared system memory. The harness now waits for the processes to exit (escalating to
SIGKILL), refuses to start while one survives, and runs a 64-token speed check that skips any config
under 20 t/s. `n5_prob` was rerun cleanly (6 s load, 22.1 GB).

Also noted: `/props` reported `speculative.types = "none"` even with MTP active, so don't trust it;
use the log's `draft acceptance … mean len` lines or the response `timings`.

## 6. Ruled out on this setup

- N ≥ 8 (verify-step cliff); plain N = 4/6/7 (no better than 5)
- `--spec-draft-p-min` at any value once probabilistic drafting is on; `--spec-draft-n-min 2`
- KV cache f16 (doesn't fit at 131k context: −72%)
- `-ub 1024` / `-ub 2048` (≤ +2.5% prompt processing for +0.5–0.8 GB VRAM)
- `--spec-type draft-mtp,ngram-mod` (−11% at long context)
- min-p 0.05 vs 0 (no speed effect; a sampling-quality choice. Note llama.cpp's default is 0.05)

## 7. Open questions

- **Prompt reuse in agent sessions.** At 30–80 s per cold prompt, how often real agent turns hit the
  prompt cache (`--cache-reuse`, `--cache-ram`) matters far more than any drafting setting.
- **Memory overclock.** Generation is memory-bandwidth bound; +1300 vs stock +1250 hasn't been compared
  (GDDR6 error retries can make an over-limit memory clock slower without crashing).
- **Confirmation.** N5 probabilistic is from one run in a separate session; a same-session A/B against
  N5 greedy would pin the size of the gain (likely 3–7%).
- **Quality.** Speed only. Probabilistic drafting is designed to leave outputs unchanged; not verified here.
